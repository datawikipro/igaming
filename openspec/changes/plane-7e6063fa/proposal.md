# Proposal: [tennisi] Проверить парсер котировок, структуру match_factor и восстановить стрим

## Context

## Description

Диагностика и восстановление стрима котировок букмекера Тенниси.

## Результаты диагностики (2026-10-04)

### 1. Парсер котировок — состояние

- HTML-парсер (`TennisiApiClient`) корректен: JSoup-based, обходит `<tr id="el...">`, маппит заголовки колонок на `TennisiOdd.groupName/name`.
- Маппинг заголовков: П1→Исход/П1, X→Исход/X, П2→Исход/П2, 1X/12/X2→Двойной шанс, К1/К2→Фора/Ф1|Ф2, <|>→Тотал/TM|TB.
- `TennisiOddsProcessor` корректен: фильтрует заблокированные коэффициенты, дедуплицирует по семантическому ключу.
- **Проблема**: при возврате maintenance-страницы сервис тихо возвращал 0 событий без явного WARN. Исправлено.

### 2. Структура match_factor — состояние

- DB schema: `factor_id VARCHAR(255)` — соответствует JPA entity (`String factorId`).
- AGENTS.md требует `factor_id INT`, но текущая реализация использует строковый `factorId` (может содержать `eventId*100+colIdx` как строку). Отклонение задокументировано — для tennisi строковый тип оправдан.
- Таблица: `id BIGSERIAL PK`, `match_id BIGINT FK`, `factor_id VARCHAR(255) NOT NULL`, `name VARCHAR(255)`, `value DOUBLE PRECISION`.

### 3. Причина нулевого стрима

- **Tennisi.bet в режиме технического обслуживания**: все endpoint-ы возвращают `Site DB in maintenance mode, please wait...`.
- Поды crawler/loader работают штатно (Running 2/2), heartbeat отправляется.
- Как только сайт выйдет из обслуживания — данные начнут поступать автоматически.

## Принятые меры

1. Добавлена детекция maintenance-страницы в `TennisiApiClient` — явный `WARN` вместо тихого возврата 0 событий.
2. Код парсера и mapper'а проверен — изменений не требуется.
3. Задача закрывается, стрим восстановится автоматически по окончании обслуживания.
